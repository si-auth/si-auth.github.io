概要・背景

複数の認可サーバー（AS）やOpenID Provider（OP）をまたぐ実案件でのトークン連鎖の問題を、IETFのIdentity and Authorization Chainingの考え方と照合。下流の認可判断で、元ユーザー、付与された権限、必要に応じて前段のResource Server情報を失わないことが中心テーマとなる。

主なポイント

  • Chainingは「誰のために始まった要求か」「何を許可されたか」「必要なら前段でどのResource Serverが呼ばれたか」をTrust Domainを越えて保持する考え方。
  • Token Exchangeは単なるトークン形式変換ではなく、下流ASへ何を渡すかを決める境界として扱う。
  • 実装上はsubject identifier mapping、data minimization、scope control/downscoping、claimsの意味と責任分界が重要になる。

話の流れ

  1. 定義：I-Dでいうchainingの3要素を整理
  2. 実案件：複数OP/AS連鎖で発生する要求をモデル化
  3. 方式比較：Identity ChainingとToken Exchangeを照合
  4. 設計論点：subject mapping・最小権限・claim semantics
  5. まとめ：Trust Domainを越える認可コンテキストの継承

OAuth SPIFFE Client Authentication 講演資料を見る ↗

概要・背景

SPIFFEのワークロードIDをOAuthクライアント認証に利用する方法を解説。共有シークレットではなく暗号学的に検証可能なSVIDをクライアント資格情報として使い、X.509-SVID、JWT-SVID、WIT-SVIDそれぞれのOAuth連携方法を整理する。

主なポイント

  • SPIFFE SVIDにはX.509-SVID、JWT-SVID、WIT-SVIDがあり、ワークロードをSPIFFE IDで識別する。
  • X.509-SVIDはmTLSベース、JWT-SVIDはJWT Client Authenticationのプロファイル、WIT-SVIDはAttestation-Based Client Authentication系の仕組みで扱う。
  • JWT-SVIDではSPIFFE Bundleから検証鍵を取得し、SPIFFE ID・aud・expなどを検証してOAuthクライアントを認証する。

話の流れ

  1. 背景：ワークロード認証とOAuthクライアント認証を接続
  2. 基礎：SPIFFE ID / SVID / Trust Domain
  3. 方式：X.509 / JWT / WIT の3系統
  4. 実装：AS側でSVIDとBundleを検証
  5. 検討：仕様ドラフト上のヘッダー・相互運用性の論点

概要・背景

会計事務所と顧問先の間の契約、会計事務所スタッフの担当割り当て、その結果として行われる委任業務を、OIDC / OAuth / AuthZEN / RAR / SSFの組合せで表現する提案。操作時点の権限だけでなく、「なぜその権限が存在するのか」を監査記録から契約まで遡れることを重視する。

  • 契約終了時にはSSFで状態変化を伝え、発行停止・再評価・失効につなげる。

話の流れ

  1. 業務背景：顧問契約 → スタッフ割当 → 委任業務
  2. 関係モデル化：Relationship / Assignment / 契約状態
  3. 認可：AuthZENで関係を評価
  4. 権限伝達：OAuth・必要に応じてToken Exchange
  5. ライフサイクル：SSFで契約終了を伝播

AI時代の「OAuth認証」にどう物申すか? 講演資料を見る ↗

概要・背景

AIサービスやMCP周辺で広がる「OAuth認証」という表現を題材に、OAuth 2.0の役割を正確に捉え直すディスカッション型セッション。OAuthは本質的に認可のためのフレームワークであり、用語の曖昧さがLLMや開発者コミュニティに波及する問題を扱う。

主なポイント

  • OAuth 2.0全体はリソースオーナーからクライアントへの認可を扱う枠組みであり、用語の正確さをLLMにも浸透させる必要性を議論する。

話の流れ

  1. 現状確認：「OAuth認証」という表現の拡大
  2. 具体例：AI/MCP関連ドキュメントでの用語使用
  3. 整理：認証と認可をOAuth 2.0のフローに沿って再確認
  4. 問題提起：LLMによる誤用の増幅
  5. 議論：正しい用語をどう広めるか

EUDIWの枠組みを出発点に民間エコシステムの在り方を考える 講演資料を見る ↗

概要・背景

企業間ID連携の個別調整コストに対し、Issuer-Holder-Verifier（IHV）型のウォレットエコシステムを民間ビジネスへ応用できないか検討。EUDIWを先行事例として、技術仕様だけでなくトラストフレームワーク、制度、運用、監査まで含めたエコシステム設計を考える。

主なポイント

  • IdP-RP型フェデレーションでは、接続先が増えるたびに契約・セキュリティ・同意などの個別調整コストが累積する。
  • IHV型ではIssuerとVerifierを疎結合にでき、Wallet経由でユーザー中心の提示・同意を作りやすい一方、初期インフラやガバナンスのコストが大きい。
  • EUDIWでは技術仕様だけでなく、トラストフレームワークや法制度・標準・役割分担までを含めてエコシステムを成立させることが重要。

話の流れ

  1. 課題：企業間ID連携の個別開発・調整コスト
  2. 仮説：IHVモデルなら参加・離脱しやすい接続形態を作れるか
  3. 先行例：EUDIWのTrust / ARFを整理
  4. 机上検証：民間ユースケースへ置き換え
  5. 結論：技術規格だけでなくトラストフレームワークが必要
